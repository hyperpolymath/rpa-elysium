== Report a vulnerability privately

Use https://github.com/hyperpolymath/rpa-elysium/security/advisories/new[GitHub private vulnerability reporting].
Private vulnerability reporting was verified enabled on 2026-10-14.
If that service is unavailable, contact j.d.a.jewell@open.ac.uk.
Email is not end-to-end encrypted; send a minimal description first and agree
on a suitable channel before sharing sensitive evidence. No verified project
PGP key or fingerprint is currently published here.

*Do not report exploitable vulnerabilities, credentials, personal data, or
private infrastructure details through public issues, PRs, or discussions.*
GitHub private reports restrict access to the participants; this policy does
not claim that GitHub provides end-to-end encryption.

Include the affected commit/version, platform, component, reproducible steps,
expected/observed behaviour, likely impact, and a minimal proof of concept.
Remove secrets and unrelated personal data. A proposed fix is welcome but not
required. For upstream dependencies, report privately here when this project
is affected and coordinate with the dependency's maintainers.

== Response and coordinated disclosure

The maintainer aims to acknowledge a report within 48 hours, triage it within
7 days, and provide updates at least every 7 days while remediation is active.
These are targets for a volunteer-maintained project, not guaranteed SLAs.
An initial disclosure target is 90 days, adjusted by agreement according to
impact, exploitation, fix readiness, and upstream coordination.

We aim to publish a tested fix, migration guidance when needed, and a GitHub
security advisory together. Credit is offered with the reporter's consent;
anonymity is respected. No monetary bounty or dedicated incident-response team
is promised. Missing a target should prompt a private follow-up, not publication
of secrets or other people's data.

== Scope and safe research

Scope includes this repository's Rust workspace, filesystem operations, WASM
plugin boundary, ABI/FFI source, configuration handling, build/deployment
workflows, and dependencies used by it.

Test only systems and data you own or have explicit permission to test. Use
isolated local fixtures. Do not perform destructive, denial-of-service, social
engineering, or production-infrastructure testing. Stop and report if you
encounter someone else's data. This policy grants no rights over third-party
systems and does not make a legal immunity guarantee on their behalf.

== Security controls and limits

* Rust check, formatting, clippy with `-D warnings`, and tests run on PRs.
* Cargo Audit rejects advisories and unmaintained dependencies; no blanket
  advisory exceptions are supplied.
* CodeQL, Hypatia and secret scanning complement review; passing a scanner is
  not proof that the application is vulnerability-free.
* Workflow refs are immutable through the committed direct/transitive action
  graph. Lock changes must be reviewed and verified with `just ci-check`.
* Read-only jobs use least-privilege tokens and do not persist checkout
  credentials. Privileged publishing/notification jobs are separate.
* Untrusted PR code is not executed in a privileged `pull_request_target` job.
* Plugin permissions, fuel limits and filesystem boundaries require manual
  threat review; the presence of WASM or Rust does not by itself prove isolation.
* Idris2 and Zig layers are present, but Rust CI is not evidence that every
  ABI proof or FFI target was compiled. See link:docs/STANDARDS-ALIGNMENT.adoc[alignment evidence and remaining gaps].

Run `just audit` and `just ci-check` before proposing dependency or CI changes.
Never commit live secrets, `.env` files, or sensitive test data.
